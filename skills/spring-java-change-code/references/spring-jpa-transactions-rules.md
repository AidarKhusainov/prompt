# Spring JPA and Transaction Rules

Use this reference before editing Spring Data repositories, JPA entities, transaction boundaries, repository queries, persistence tests, or behavior that depends on database semantics.

## Transaction boundaries

Prefer transaction boundaries in the service/application/use-case layer, following the project's existing architecture.

Do not put transaction orchestration in controllers or transport adapters unless the project already has that pattern and the scope is clear.

Do not broaden transaction scope casually. Long transactions can hold locks, increase contention, hide lazy-loading problems, and couple unrelated operations.

Treat transaction-boundary changes as permission-gated when they affect public behavior, consistency, rollback, locking, retries, idempotency, or integration side effects.

## Rollback semantics

Before changing rollback behavior, check the project's Spring version and existing conventions.

Be careful with:

- checked vs unchecked exceptions;
- explicit `rollbackFor` and `noRollbackFor`;
- nested transactions and savepoints;
- `REQUIRES_NEW` and side effects that must commit independently;
- read-only transactions;
- transaction boundaries around external calls;
- events published before or after commit.

Do not hide persistence errors with broad catches, silent fallbacks, or swallowed exceptions.

## Lazy loading and object graphs

Do not fix lazy-loading failures by exposing entities directly from web controllers or by expanding transactions through the web layer.

Prefer explicit fetching, DTO mapping, repository queries, projections, or application-layer assembly that matches the repository's style.

Be careful with bidirectional relationships, recursive serialization, `OpenEntityManagerInView` assumptions, and accidental loading of large graphs.

## N+1 and query behavior

When changing queries or mapping behavior, consider N+1 regressions, deterministic ordering, pagination correctness, fetch joins, entity graphs, projections, count queries, and database-specific semantics.

Do not add eager fetching globally to fix one use case unless the project already uses that pattern and the wider impact is understood.

Do not silently switch to H2 or an in-memory substitute when production database-specific behavior matters.

## Repository changes

Preserve repository method contracts, query parameter semantics, sorting, pagination, locking behavior, and null/empty result behavior unless explicitly requested.

Prefer existing repository style: derived queries, `@Query`, specifications, Querydsl, Criteria API, custom repository implementations, jOOQ, JDBC, or another project convention.

Do not introduce a new persistence abstraction for a small query change.

## Schema and migrations

Database schema, migration, constraint, index, column type, and generated DDL changes are permission-gated unless explicitly requested.

Do not edit generated migrations or generated metamodels directly unless the repository workflow requires it.

If a change needs a migration, call out compatibility, rollback, data backfill, and deployment ordering implications.

## Persistence testing

Test repository and transaction behavior against the narrowest reliable persistence boundary.

Use existing real DB, test DB, data-slice tests, or Testcontainers infrastructure when behavior depends on:

- SQL dialect;
- constraints and indexes;
- JSON/array/db-specific column types;
- locking;
- transaction isolation;
- rollback/commit behavior;
- pagination and sorting generated by the database;
- JPA dirty checking, flushing, cascading, or orphan removal.

Do not mock repositories when the changed behavior depends on real SQL/JPA semantics.

Use focused unit tests for pure query-parameter preparation, predicate-building helpers, or mapping logic that does not require Spring/JPA.

## Self-review

Before finishing, check that:

- transaction boundaries are still intentional;
- rollback behavior is explicit when it matters;
- lazy loading is not hidden by a broader web transaction;
- queries are deterministic and pagination-safe;
- no N+1 issue was introduced for common paths;
- schema or migration changes were gated;
- tests prove the observable persistence behavior rather than repository mock calls.
